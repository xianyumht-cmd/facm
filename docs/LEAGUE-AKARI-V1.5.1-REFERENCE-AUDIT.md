## Compatibility, quality and acceptance rules

1. User reports hands-on successful Tencent-server usage of Akari. The upstream README support disclaimer is **not proof of technical non-functionality**. Still validate each GGman endpoint and behavior with authenticated, human-operated Chinese LOL test sessions before shipping.
2. GGman remains native WinForms, lightweight, and based on its existing `LayeredFloatingBall` and approved compact panel. **Never change visual geometry or orb behavior** under the pretext of porting an Akari feature. Do not introduce Electron, embedded Chromium, a second LCU monitor or always-on multiple network pollers.
3. Research process per feature: read pinned v1.5.1 **settings -> controller -> API client/writer -> error/fallback -> lifecycle -> tests**, then compare existing GGman equivalents. Classify **already implemented**, **partial**, **missing**, or **blocked pending a named proof/dependency**. No Akari feature may be classified as "not practical" or removed from the target set because its existing Electron implementation cannot be reused. Source presence alone must not become a "GGman complete" checkbox.
4. New features must be opt-in when they mutate LCU state. Preserve writer authorization, queue restrictions, delayed task cancellation, read-after-write confirmation, phase cancellation and process cleanup.
5. Source-aware network issues: especially Tencent LCU region, external ranking patches and SGP authentication. Never fabricate a tier/ranking because an upstream endpoint is blocked.
6. Diagnostics are part of each feature: one correlation ID across interaction, LCU read/write, remote provider, cache and render; export sanitised, bounded component logs alongside `facm-YYYYMMDD.log`. Avoid account IDs, tokens, private chats, raw LCU payloads and any personal identifiers.
7. Prove the runtime/CPU benefit on user-class Windows 10 hardware: cold start, private working set, idle CPU, active ChampSelect CPU, allocations and resource cleanup. Binary size alone is not a performance metric.
8. Keep PR #355 Draft, no production release/merge, and no claim of archival binary reverse engineering. Maintain MIT attribution if reusing actual copyrighted source, not just functional concepts.

### Highest-value low-risk candidate implemented in this slice

1. Repair the draft Rift public standings reader's too-short network budget. The 2026-10-25 previous Windows probe read ARAM 26.21 correctly, but `rift-top valid=False` despite HTTP 200 and 864 public ranked rows. An independent fetch of that roughly 2.16 MB page required **3.95 s** against GGman's **3.2 s** transport deadline. Candidate budget is 8 s, still cancelable on panel close/role change. Follow-up [Glass CI #40176052137](https://github.com/xianyumht-cmd/facm/actions/runs/40176052137) on code SHA `8fa2fddd` now reports **`rift-top valid=True expanded=True patch=26.21 all_rows=173`**, ARAM complete at 173, and sanitized query timing. This validates the actual C# parser on the GitHub runner, **not** the mainland no-VPN transport or Riot/Tencent patch identity.
2. Implement Akari's existing pending-invitation queue safety rule in GGman's existing `LeagueMatchmakingAutomationController`. No second read/write endpoint, watcher, timer or setting is introduced. With auto-matchmaking already enabled, `invitations[*].state=Pending` blocks the POST until a later normal Lobby observation shows it settled. Offline tests cover pending/settled/declined and exactly-once behavior. No request payload or member ID is logged.
3. Keep auto ban/pick, automatic bench trading, local player tags, SGP and in-game timers in the **mandatory parity queue** with explicit write/privacy/performance gates. Full scope is committed; parity and live-Tencent acceptance are **not** established by this matrix.
