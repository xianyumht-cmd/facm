## Build #304 首次加载修复

### 1. 下载断点续传

旧实现：

- 随机 `.partial-<guid>` staging；
- 中途退出后下一次无法可靠复用上次下载结果；
- 用户实机第二次启动曾再次看到 `36/538`，说明首次下载体验不够稳定。

新实现：

- 固定 staging：`%LOCALAPPDATA%\FACM\PetHost\Assets\.vpet-ac77ba14.partial`；
- 启动时逐文件按 Git tree size 校验；
- 已完整的文件直接跳过；
- 旧 `.partial-*` 会尽量恢复最新一份；
- 单文件先写 `.download`，大小正确后原子替换；
- 中断后保留 staging，下次继续缺失文件；
- 下载并发从 8 提高到 20。

正式完成缓存仍为：

`%LOCALAPPDATA%\FACM\PetHost\Assets\vpet-ac77ba14\`

### 2. 修复第一次动作缓存可能长期等待

已查到 VPet 官方桌面程序在创建 PNG 动画前会设置：

`PNGAnimation.MaxLoadMemory = MemoryUsage + MemoryAvailable / 2`

而 `VPet-Simulator.Core` 默认值只有 **2000 MB**。

旧 PetHost 没有复制这段初始化。第一次 538 个高分辨率文件开始合并 PNG 动作缓存时，进程工作集可能碰到默认阈值，后续 `PNGAnimation.startup()` 会反复等待 `Function.MemoryUsage() <= MaxLoadMemory`。这与“第一次在建立动作状态机长时间不动、第二次重开正常”的实机表现吻合。

Build #304 已按 VPet 官方 x64 启动逻辑动态设置 `PNGAnimation.MaxLoadMemory`，并在真正构建 Graph 前完成。

### 3. 不再让 WPF UI 同步死等 `LoadALL()`

VPet Core 1.1.0.66 的 `Main.LoadALL()` 内部会同步：

`Load_2_WaitGraph(...).Wait()`

旧 PetHost 直接在 WPF UI 线程调用 `_main.LoadALL()`，所以首次生成动作缓存期间加载卡片本身也无法正常刷新，看起来像程序死了。

Build #304 改为：

- `LoadALL()` 在后台工作线程执行；
- 利用 VPet 已有 `WaitCountAction` 回传真实动画准备数量；
- 加载界面显示 `正在生成动作缓存 x/y`；
- 明确提示“首次启动会比之后慢”；
- 完成后再淡入真正桌宠；
- `ready` IPC 附带 `graphs=<数量>` 和 `startup-ms=<耗时>`，后续日志能直接衡量首次启动时间。

## FACM 单击命中范围修复

旧实现的 `PreviewMouseLeftButtonUp` 只判断：

- 鼠标移动不超过 7 px；
- 650 ms 内松开；

然后无条件发送 `event|click`，所以整个透明 PetHost 窗口都是 FACM 控制面板入口。

Build #304 现在只在 VPet 自己配置的：

- `TouchHeadLocate + TouchHeadSize`
- `TouchBodyLocate + TouchBodySize`

这两块人物区域内发送 FACM `click`。

**没有设置 `e.Handled`，因此 VPet 原本摸头、摸身体、长按 Raised/提起等左键互动继续按原逻辑运行。**

长按拖动不要修改。用户已确认 VPet 的原始设计就是长按后拖动，并且实际可用。
