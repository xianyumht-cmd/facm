## 5. 已解决的 Win10 / Personalization 历史根因，不要重新走

### 5.1 旧 WinUI brush `E_ACCESSDENIED`

真实 Win10 曾在：

```text
ABI.Microsoft.UI.Xaml.Media.ISolidColorBrushMethods.set_Color
```

触发 `UnauthorizedAccessException / E_ACCESSDENIED`。

根因：FACM semantic brush 直接 alias 到 WinUI 平台/system brush，运行时修改了平台拥有对象。

修复规则：

- platform/system ThemeResource 只能读；
- FACM semantic brush 必须 app-owned；
- theme runtime 只修改 FACM-owned brush；
- personalization startup fail-soft。

**不要重新用“直接修改平台 brush”路线。**

### 5.2 Personalization 永久灰色：one-shot UI sync 不够

旧 UI 手动调用 `SyncPersonalizationSurface()`；如果 async bootstrap 当时 `IsBusy=true`，控件被 disable 后没有可靠 completion refresh。

修复：

- `PersonalizationViewModel.PropertyChanged`
- DispatcherQueue 回 UI owner
- 连续 state sync
- pet runtime / state diagnostics

之后还将 Busy 状态文本改为：

```text
正在处理，请稍候…
```

避免“准备就绪 + 所有控件灰掉”的误导。

**如果未来控件灰掉，先看 VM/runtime JSONL 是否 Busy，而不是先继续加 UI refresh。**

### 5.3 first-chance UnauthorizedAccess 不等于 fatal startup crash

旧 `startup-crash.json` 曾捕获 `System.IO.FileSystem.MoveFile` 的 first-chance UnauthorizedAccess，但 recovery state 仍是 Running；这种异常可能被 repository fail-soft 捕获。

以后判断 crash 必须结合：

- recovery state
- stack
- lifecycle events
- process behavior

不要只看 `startup-crash.json` 文件存在就判 fatal。

## 6. Batch M：最新真机缺陷、失败路线和根因

### 最新 Win10 evidence 实际证明什么

最新 targeted evidence：

- recovery state：`Running`
- app version：`4.0.0.0`
- `consecutiveFailures=0`
- LKG：theme `glass-blue`、pet `moth`、`enabled=false`、F `1569,576`
- greenfly -> dragonfly -> moth 的“选择”流程完成
- 点击启用 moth 后：

```text
pet-enable-start
IsBusy=true
payload-preparing
```

之后 evidence 窗口超过 13 秒仍没有：

```text
host-starting
ready
failed
pet-enable-finish
```

但同期 F drag-position-saved 继续出现。

结论：**FACM 主 UI/message loop 没死，真正长耗时点在 PetHost payload prepare。**

### 为什么之前的 PetHost 修复还不够

此前已经做过：

- process-local `_cachedPreparation`
- 同一 stream hash/extract
- cancellation-aware extraction
- 60 秒 preparation timeout
- enabled 只在 runtime ready 成功后持久化
- 同一 store/process 重复 prepare smoke

这些解决了“同进程反复切换”的问题，但 **没有解决关闭 FACM 后再开一个新进程**。

旧逻辑每个新进程仍然必须：

1. 打开内嵌 `PetHostBundle.zip`；
2. 完整 SHA-256 约 76.9 MB；
3. 得到 SHA 后才知道 `runtime/pethost-host/<sha>` 是否已经有完整 disk cache。

所以即使磁盘 cache 已存在，新进程为了“知道 cache key”仍先做一次大文件 hash。

### 为什么旧 24 次 PetHost smoke 没抓到

24 次测试都在**同一个 store/process**内；第一次后 `_cachedPreparation` 直接返回，因此测试证明了 in-process cache，却没有模拟“退出 FACM -> 新进程 -> 使用旧 disk cache”。

这是明确的测试覆盖缺口。

### Batch M 根因修复

代码 head：`6ba8c917c73e9f7eee1229b29ba9ed243be8ae83`

- Foundation 打包 PetHost ZIP 后生成 `out/PetHostBundle.sha256`；
- FACM.App 同时嵌入：
  - `FACM.Resources.PetHost.zip`
  - `FACM.Resources.PetHost.sha256`
- `RequirePetHostBundle=true` 时 ZIP 或 SHA identity 缺一都 build fail；
- 新 FACM 进程只读 tiny SHA identity，就能直接检查 exact disk cache；
- **完整 cache hit 时不得打开/rehash 76.9 MB embedded ZIP；**
- local/lightweight build 缺 identity 时仍保留安全 hash-on-demand fallback；
- WindowsSmoke 创建 fresh `WindowsPetHostBundleStore` 模拟新进程，要求已有 cache 时 `openBundle == 0`；
- source gate 固化 `Cross-process PetHost cache no-rehash` contract。

## 9. 失败/不足方案及原因：明确不要重复

### 不足路线 1：把所有灰色都当 UI 刷新问题

第一次 stale-disabled 的确是 UI sync 问题；但最新 JSONL 已证明 `IsBusy=true` 是真实 VM busy，卡在 `payload-preparing`。继续只加 `PropertyChanged`/Dispatcher 不会解决大包 prepare。

### 不足路线 2：只靠同一进程 PetHost cache smoke

同 process/store 的 `_cachedPreparation` 会掩盖 disk cache lookup 前的大包 rehash。以后缓存测试必须包含 fresh store / fresh process 语义。

### 不足路线 3：单纯继续加 PetHost timeout

timeout 只能避免无限 Busy，不能让正常跨进程 cache hit 变快。Batch M 已从 cache identity 根因修复，不要再把 timeout 当性能修复。

### 不足路线 4：Settings2 whole-document Save

多个 feature 并发会 lost update。不要重新引入 `Load -> 修改局部 -> Save whole document`；必须走 atomic narrow `UpdateAsync`。

### 不足路线 5：为了旧 source gate 把代码改回 SaveAsync

旧 gate 曾硬编码期待 `SaveAsync`。正确处理是升级 gate 到 atomic contract，不要为了 CI 让架构退回旧写法。

### 不足路线 6：Updater fallback 流式覆盖 live EXE

中途 kill 可能留半文件。禁止恢复 `File.Copy(..., liveDestination, overwrite:true)` fallback/rollback。

### 不足路线 7：把 first-chance exception 当 fatal

必须结合 recovery state / lifecycle / stack。不要只因 diagnostics 里出现 UnauthorizedAccess 就判应用崩溃。

### 不足路线 8：继续做“用户测一个 bug -> 修一个包”

后续必须先让代码审查、自动 smoke 和重复压力发现基础问题。用户真机主要做最终产品/平台验证。

### 明确禁止的方向

- **不回退 3.5 架构**；可以对齐 3.5 行为和产品基线。
- 功能等价验收前 **不开始 UI 2.0**。
- 不创建 P7 的新版本分支。
- 不把 #632 CI 当成整个 Win10/Gate13 PASS。
