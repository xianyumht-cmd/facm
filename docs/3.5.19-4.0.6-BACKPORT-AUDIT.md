## 1. 产品约束与审计原则

后续 FACM/GGman 以 3.5.19 的 .NET Framework 4.8 / WinForms 轻量模型为主线：

- 保留 `src/FACM` 的轻量单进程、WinForms、快速启动体验。
- 保留当前 3.5.19 海符/Mayhem 数据链。它的实际加载速度表现好，不允许为了“架构统一”替换成更重的 4.x 数据栈。
- 4.x 中有用户价值的能力只允许按“最小可回灌单元”吸收：算法、去重、状态栅栏、节流策略、生命周期规则、失败恢复规则。
- 不为回灌功能引入 WinUI 3、Morphing Surface、完整 `FACM.Core` / `FACM.Infrastructure` / `FACM.Platform.Windows` 分层、native bootstrapper、CAB、多版本目录和大型 self-contained 主运行时。
- 不做安全加固类审计；SHA、签名、anti-tamper 等只有在直接影响普通功能/更新链时才考虑。
- 不把 4.x 的 bug 当成 3.5.19 的 bug；所有结论按实际源代码分别归属。

## 2. 体系结构结论

### 2.1 3.5.19

3.5.19 的核心形态是 WinForms 主程序 + 少量内嵌辅助组件。League 功能并不是“每个页面完全各自乱轮询”：它已经有 `LeagueGameflowMonitor`、缓存的 `LeagueClientRuntime`、`LeagueClientWriteRuntime`、Bench/Build/Presence/PostGame/Matchmaking 等独立服务。

这意味着 3.5.19 自动化比 4.x 慢，**主要不是因为缺少 4.x 分层架构，而是具体的等待策略和状态触发方式更保守**。这是本轮最重要的判断之一。

### 2.2 4.x

4.x 最新线把产品拆为：

- `FACM.Core`：纯契约、状态/策略；
- `FACM.Infrastructure`：设置、在线更新、League、诊断、恢复；
- `FACM.Platform.Windows`：Windows 进程/窗口/League/桌面适配；
- `FACM.App`：WinUI 3 UI 与 composition root；
- Bootstrapper / smoke / updater / PetHost 等独立组件。

4.x 的真正优势不是“层数更多”，而是几个运行时 owner 被统一：**一个 session owner、一个 Gameflow owner、统一 heartbeat、统一状态去重、明确 generation/fencing、明确 teardown。** 这些思想可以用很小的代码量回灌到 3.5.19，而不需要搬整套架构。

## 4. 自动化响应速度：已确认的根因

用户反馈“3.5.19 自动化没有 4.x 反应快”与源码一致。

### 4.1 3.5.19 Gameflow cadence

`src/FACM/League/LeagueGameflowMonitor.cs`：

- 未连接/无客户端：**10 秒**；
- ChampSelect：2 秒；
- Matchmaking / ReadyCheck：3 秒；
- InProgress / GameStart：10 秒；
- 其它连接状态：5 秒。

### 4.2 3.5.19 自动寻找对局

`src/FACM/League/LeagueMatchmakingAutomation.cs`：

- Lobby 自动搜索在触发后先固定等待 **1500 ms**；
- 随后才按 3000 ms 观察/执行。

### 4.3 3.5.19 自动接受

同一服务中 ReadyCheck 自动接受先固定等待 **450 ms**，再确认状态并执行 accept。

### 4.4 4.x

4.x `LeagueMatchmakingAutomationService` 直接消费共享 Gameflow heartbeat，在状态有效时立即评估；没有 3.5 这两个固定额外 sleep。它通过 dedupe / generation / episode fencing 避免重复动作，而不是靠“先等一会”降低竞态概率。

4.x 未连接/连接失败状态的 Gameflow cadence 约 **3 秒**，也比 3.5 的 10 秒更快恢复发现。

### 4.5 结论

自动化速度差主要来自**实现策略**而不是“WinForms 架构天生慢”：

| 路径 | 3.5.19 额外等待 | 4.x | 可轻量修复 |
| --- | ---: | ---: | --- |
| Lobby 自动搜索 | 1500 ms | 无固定等待 | 是 |
| ReadyCheck 自动接受 | 450 ms | 无固定等待 | 是 |
| 无客户端/断线后重新发现 | monitor 最长约 10s cadence | 约 3s | 是 |
| ReadyCheck 基础 Gameflow polling | 3s | 3s | 不需要架构迁移 |

**建议 P1：**

1. 移除或极小化 1500 ms Lobby 初始延时；
2. 移除或极小化 450 ms ReadyCheck 延时；
3. 断线/Connecting/NotRunning cadence 从 10s 收紧到约 3s；
4. 把 4.x 的 episode/generation/dedupe 思想以轻量字段移入 3.5，防止响应变快后重复 POST；
5. 不迁移 4.x `LeagueHttpGateway` / Core/Infrastructure 分层。

这是高收益、低重量的最佳实践回灌。

## 5. 3.5.19 海符/Mayhem：保留现有高速数据链

### 5.1 为什么当前体验快

`MayhemAutomaticGuideService` 已经具备：

- 10 分钟本地缓存；
- fast/normal 查询策略；
- 英雄身份、Mayhem 查询、强化排行、本地化并发 fan-out；
- 有界等待；
- 失败时允许部分结果而不是把整个 UI 卡死。

因此**不要把它替换成 4.x 的 service stack**。4.x 只作为展示/状态边界参考。

### 5.2 已确认的 `5350.0%` bug

3.5.19 的 `OpggMayhemService.Rate()` 已经把 `0..1` 输入归一化成 `0..100` 百分点。

但 `LeagueChampSelectAssistantForm` 又执行：

```csharp
result.WinRate * 100d
```

并且通用 `FormatRate()` 同样再次 `* 100d`。

所以 `53.5` 会显示成 `5350.0%`。这是**确认的双重放大**，不是接口返回异常。

当前 smoke 又用类似 `0.5432 -> 54.3%` 的假设测试 UI，实际上把错误的单位契约固化进了测试。

**修复：**UI 层直接 `value.ToString("0.0") + "%"`；测试输入改成 `54.32`，期望 `54.3%`。以后最好把字段命名明确为 `WinRatePercent` / `PickRatePercent`。

### 5.3 “显示不全”已确认的来源

轻量助手存在固定尺寸和显式截断：

- expanded 大小固定在约 `660×458`；
- guide panel 宽度约 332；
- 强化排行 ListView 高度约 118；
- 多个 Label 使用 `AutoEllipsis`；
- core items 呈现只取前 7 条；
- service 侧还有 bounded sanitize 上限。

所以用户看到“数据加载很快但内容没展示全”与代码一致。修复重点应是**呈现层**：

- 保留 collapsed 小条；
- expanded guide 根据工作区/DPI 自适应高度；
- 详细区域可滚动；
- ellipsis 项提供完整 tooltip；
- 不无理由只显示前 7 个 core item；
- 强化排行保留现有数据缓存，只改善滚动/分页/可视行；
- 不引入新的网络请求链。

## 6. 3.5.19 按钮文字残影/重绘 bug

`src/FACM/Theming/FacmDesignSystem.cs` 的 `FacmNavButton` 是高置信根因：

- `BackColor = Transparent`；
- 开启 `UserPaint` / `AllPaintingInWmPaint` / `OptimizedDoubleBuffer`；
- `OnPaint` 没有调用 `base.OnPaint`，也没有稳定重画完整背景；
- idle fill 只有 `Color.FromArgb(8, Surface)`，几乎透明；
- hover 时 `Invalidate()` 且使用更实的 fill，所以鼠标移上去立刻恢复正常。

这与“鼠标不在按钮时多个旧文字像叠在一起，移上去瞬间正常”的症状高度一致。

**最小修复：**idle 状态改为确定性的非透明填充，并确保每一帧完整覆盖旧像素。

注意不要盲目 `Graphics.Clear(Parent.BackColor)`：父容器若自绘渐变/玻璃背景会出现色块接缝。应按实际父容器选择“按钮自身完整不透明背景”或正确重绘父背景。

回归必须覆盖：静止鼠标下重复改文字、窗口遮挡/恢复、最小化恢复、100/125/150/200% DPI、hover/selected/disabled/theme change。

## 7. 进游戏自动隐藏：回灌行为，不搬 4.x 状态机

4.x 主 Morphing Surface 有明确流程：Gameflow 进入 InGame → `HiddenInGame` → `AppWindow.Hide()`。

这个用户体验值得 3.5.19 保留，但 4.x 后期也证明“多个 UI/pet owner 都能决定可见性”会造成冲突。因此 3.5 不应复制整套状态机，只需建立一个轻量可见性规则：

- GameStart / InProgress / Reconnect / WatchInProgress：隐藏 FACM/GGman 桌面入口；
- PostGame/Lobby：如果之前是**因游戏自动隐藏**，自动恢复；
- 用户主动隐藏/关闭：游戏结束不能擅自恢复；
- 游戏内用户从托盘主动打开，可记录 manual override；
- 桌宠/飞行入口和默认悬浮入口必须服从同一个 game-suppression 状态。

最小实现可用 `autoHiddenByGame` + `manualOverride`（或一个很小的 reason enum），不需要 `FacmSurfaceStateMachine`。

## 8. 4.x 最值得保留的“最佳实践”

### P1：强烈建议回灌

1. **自动化即时评估 + episode/generation 去重**：替换固定 1500ms/450ms 等待。
2. **断线阶段更快 heartbeat**：10s → 约 3s，仅在 NotRunning/Connecting/ClientError 收紧。
3. **单一状态事实**：自动化继续消费现有 3.5 Gameflow，不为每个功能新增 timer。
4. **异步 stale-result fencing**：查询完成前保存 generation/signature，完成后只提交当前 episode。
5. **明确 teardown**：窗体关闭/进程关闭时取消 CTS、解绑事件、dispose timer，避免旧任务回写新 UI。
6. **进游戏可见性 suppression**：按原因隐藏/恢复，而不是所有模块各自 Show/Hide。

### P2：按问题证明后回灌

- 认证失效时的一次 session invalidate + retry；
- 结构化 diagnostics 的最小字段集；
- settings LKG 的轻量版本；
- remote-support 需要时的日志筛选/诊断导出。

### 不回灌

- WinUI 3 / Morphing Surface；
- `FACM.App` 宿主；
- 完整 `FACM.Core` / `Infrastructure` / `Platform.Windows` 新依赖层；
- Bootstrapper/CAB/多版本 `.facm/versions` 分发；
- 4.x Product State/Performance Budget 整体架构；
- 4.x 大型 self-contained 主程序；
- 为了“统一”重写现有 3.5 Mayhem 数据服务。

### 高概率 4.x-only，可在最终 cleanup 删除

需在 cleanup commit 前做一次 project-reference/workflow 引用扫描，确认 3.5 构建无引用后删除：

- `src/FACM.App`；

## 13. 最终产品决策

3.5.19 已经不是“落后的旧架构”。对当前产品，它反而拥有更合适的轻量 UI、快速 Mayhem 链、成熟的 net48 单 EXE 维护方式。4.x 最值得留下的不是 WinUI/大分层，而是：

**更少的固定等待、更明确的单一事实源、更严格的去重/episode fencing、更干净的生命周期和失败恢复规则。**

这些完全可以以很小的代码量回灌到 3.5.19。

因此后续路线确定为：

> **保留 3.5.19 的形态和速度 → 修已确认 UI/单位 bug → 吸收 4.x 的响应与可靠性最佳实践 → 完整回归 → 删除 4.x-only 主线资产。**
