## 1. 长期产品决策

FACM 后续只维护 **3.5.x lightweight**：

- 主程序继续使用 `src/FACM` 的 .NET Framework 4.8 / WinForms 架构。
- 正式 3.5 构建保持轻量单 `FACM.exe`，当前 CI 硬门槛 < 10 MiB。
- `FACM.PetHost` 仍作为可选 VPet 运行时源码保留并 build/self-test，但普通 3.5 EXE **不内嵌 self-contained PetHost bundle**。
- 4.x 只作为功能、状态机、生命周期和故障经验参考，不再继续作为独立产品线。
- 不回灌 WinUI 3、`FACM.App`、`FACM.Core/Infrastructure/Platform.Windows` 分层、CAB、native bootstrapper、`.facm/versions`、4.x migration、.NET 10 self-contained 主程序。
- 4.x 有价值能力必须用 3.5 当前 service/session/WinForms 边界重实现或直接复用 3.5 已有能力。

## 2. 审计纪律

- **3.5.19 缺陷**：必须在 `v3.5.19`/当前 3.5 代码中实际存在；

## 4. 已确认并修复的 3.5.19 问题

### 4.1 Mayhem 百分比双缩放

3.5 Mayhem model/service 的 `WinRate` / `PickRate` 使用 **0..100 百分点**。ChampSelect 显示层又乘一次 100，导致 `53.5` → `5350.0%`。

修复：UI 直接格式化百分值；smoke 以 `54.32 -> 54.3%` 验证单位契约。

### 4.2 Mayhem 展示不全

原问题在显示层，不在数据链：固定高度、ellipsis、较小 augment list、core item 人为截断使部分数据不可见。

修复：扩大攻略区、AutoScroll、增加行高/tooltip、装备展示容量提高、augment list 增高。**没有替换 `MayhemAutomaticGuideService` 的缓存/并发/有界等待/fail-soft 路线。**

### 4.3 导航按钮文字残影

`FacmNavButton` owner-draw 使用透明背景 + 极低 alpha idle fill，又未保证每帧覆盖旧像素。hover 变成更不透明填充时旧像素被覆盖，所以鼠标划过会“突然正常”。

修复：普通态使用确定性不透明 Surface 填充；仍需 Windows 多 DPI 实机 Gate。

### 4.4 紧凑主控面板裁剪残影

用户视频显示的是另一条链：`CompactMenuForm` 基准高 680，enhancer 再缩到约 236；旧路径有机会先 show/paint 大窗口再裁剪，桌面合成后出现横条/旧面板碎片。

修复：构造 form 后，在 `PositionMenu()` 和首次 `Show()` **之前**执行 `DesktopLauncherEnhancer.Apply()`，首帧直接使用最终紧凑 geometry。

## 5. 自动化为什么 3.5 体感比 4.x 慢

结论：主要是**代码等待策略**，不是必须替换架构。

3.5 原行为：

- disconnected / no client：10 秒；
- ChampSelect：2 秒；
- Matchmaking / ReadyCheck：3 秒；
- InGame：10 秒；
- 其它 connected：5 秒；
- Lobby automation 首次再固定等 1500 ms；
- ReadyCheck accept 再固定等 450 ms。

4.x 有价值之处是：共享 Gameflow heartbeat 到达后立即评估，并用 episode/generation/dedupe 限制副作用；NotRunning/Connecting/ClientError 约 3 秒重获。

3.5.19 P1 已改为：

- disconnected/null cadence 10s → 3s；
- 删除 Lobby 1500ms；
- 删除 ReadyCheck 450ms；
- 保留 3.5 当前 monitor/session 架构。

## 6. 自动寻找的失败与模糊结果语义

提速后继续审计发现一个重要边界：

- 如果 fingerprint 在 POST **之前**就提交，真实网络/服务器失败会导致整个当前 Lobby 永远不重试；
- 如果只看 response 并在失败后无条件重试，又会遇到另一种风险：LCU 已接收 POST，但客户端在返回响应前 timeout/reset，下一轮会重复 POST。

当前 3.5.19 使用轻量 postcondition 方案：

1. 正常 POST 2xx：提交 Lobby fingerprint，结束；
2. response 为失败/null：只在此时额外读取一次 `/lol-matchmaking/v1/search`；
3. 若 `isCurrentlyInQueue=true`：权威状态证明队列已启动，提交 fingerprint，不再 POST；
4. 若 false/缺失/读取失败：不消费 fingerprint，既有 3 秒 observer 可以再次尝试。

因此：

- 正常成功路径**没有额外预读**，不牺牲刚获得的响应速度；
- 真失败可恢复；
- “写已生效但响应丢失”不会因为盲 retry 形成重复 POST。

ReadyCheck 仍采用每 episode 一次 attempt 的保守 exactly-once 语义，不在本批做自动重试风暴。

## 7. InGame 自动隐藏

没有移植 4.x `FacmSurfaceStateMachine`。3.5 增加一个很小的 `DesktopEntryGameflowPolicy`：

- `GameStart` / `InProgress` / `Reconnect` / `WatchInProgress` → InGame suppression；
- 只有“Gameflow 自己隐藏了原本可见的入口”才获得赛后 restore ownership；
- 原本已隐藏的入口不被强制恢复；
- 复用唯一 `LeagueDashboardModule` / `LeagueGameflowMonitor`，无第二套 timer；
- LCU 不可连接时，如果 `League of Legends` 游戏进程仍存在，3.5 activity fallback 继续判 InGame，降低断连时过早恢复。

普通球、Sprite、VPet 都使用非破坏性 hide/show。PetHost 的 desired visibility 在 host 尚未启动完成时也会记录，避免 InGame 期间晚启动重新闪出。

## 8. 轻量构建审计新发现

继续审查发现 3.5 仓库曾同时存在两种相互冲突的构建语义：

- 当前 GitHub `build.yml` / `publish-3.5-lightweight.yml`：PetHost 只 build/self-test，FACM.exe 不内嵌大 bundle，< 10 MiB；
- 旧 `scripts/build-release.ps1` / `.github/workflows/publish-release.yml`：publish self-contained PetHost、压 ZIP、`RequirePetHostBundle=true`，构建重型 embedded-PetHost EXE。

P1 已修正本地路径：

- `FACM.csproj` 默认 `IncludePetHostBundle=false`；残留 `out/PetHostBundle.zip` 不再能悄悄膨胀普通构建；
- 显式历史/专项构建仍可通过 `IncludePetHostBundle=true` 或 `RequirePetHostBundle=true` opt-in；
- `scripts/build-release.ps1` 已改为与 lightweight CI 一致：build/self-test PetHost，但不 embed，并检查 EXE < 10 MiB。

旧 `.github/workflows/publish-release.yml` 已确认与未来 lightweight publisher 冲突，**不在 #241 删除**，但已移入清理清单的 `DELETE AFTER GATE`。canonical 3.5 发布入口是 `.github/workflows/publish-3.5-lightweight.yml`。
